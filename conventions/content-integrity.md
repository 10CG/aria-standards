# 内容真实性规则

> **Version**: 2.2.0
> **Status**: Active
> **Purpose**: 确保所有文档和代码内容的真实性、准确性和一致性

---

## 1. 核心原则

### 1.1 三大支柱

| 支柱 | 说明 | 重要性 |
|------|------|--------|
| **真实性** | 所有信息必须基于事实 | 最高 |
| **准确性** | 数据和描述必须精确 | 最高 |
| **一致性** | 内容在各处保持统一 | 高 |

### 1.2 适用范围

- 文档内容 (Markdown, README, etc.)
- 代码注释
- 提交消息
- API文档
- 测试描述
- 配置文件注释

## 2. 禁止虚构信息

### 2.1 人员信息

```yaml
❌ 禁止:
  - 虚构人名: "张三", "John Doe", "测试用户"
  - 虚构邮箱: "test@example.com" (在正式文档中)
  - 虚构联系方式

✅ 正确做法:
  - 使用角色描述: "项目负责人", "前端开发者"
  - 使用占位符并标注: "[待填写]", "TBD"
  - 明确标记示例: "示例: user@example.com"
```

### 2.2 日期和时间

```yaml
❌ 禁止:
  - 使用未来日期作为已完成事项
  - 虚构历史日期
  - 不准确的时间戳

✅ 正确做法:
  - 使用实际日期: "2025-12-14"
  - 不确定时标注: "待定", "TBD"
  - 计划日期明确标记: "计划: 2025-12-20"
```

### 2.3 功能状态

```yaml
❌ 禁止:
  - 将未完成功能标记为已完成
  - 虚构测试覆盖率
  - 夸大功能描述

✅ 正确做法:
  - 准确标记状态: "进行中", "已完成", "计划中"
  - 使用实际数据: "覆盖率: 45%"
  - 明确说明限制: "当前仅支持..."
```

## 3. 日期规范

### 3.1 格式标准

| 场景 | 格式 | 示例 |
|------|------|------|
| 文档日期 | YYYY-MM-DD | 2025-12-14 |
| 时间戳 | ISO 8601 | 2025-12-14T14:30:00+08:00 |
| 年月 | YYYY-MM | 2025-12 |
| 相对日期 | 明确描述 | "3天前", "下周一" |

### 3.2 时区处理

```yaml
规则:
  - 默认使用本地时区 (UTC+8)
  - 跨时区场景标注时区
  - Git提交使用本地时间

示例:
  ✅ "2025-12-14T14:30:00+08:00"
  ✅ "2025-12-14 (北京时间)"
  ❌ "2025-12-14T14:30:00" (缺少时区)
```

### 3.3 文档日期更新

```yaml
更新时机:
  - 内容实质性变更时更新 updated_at
  - 格式调整不需更新
  - Changelog 必须记录重大变更

YAML Frontmatter 示例:
  ---
  created_at: '2025-12-01'
  updated_at: '2025-12-14'
  ---
```

## 4. 引用真实性

### 4.1 文件路径

```yaml
❌ 禁止:
  - 引用不存在的文件
  - 错误的相对路径
  - 过时的文件引用

✅ 正确做法:
  - 验证路径存在
  - 使用相对路径优先
  - 定期检查链接有效性
```

### 4.2 外部链接

```yaml
规则:
  - URL 必须可访问
  - 引用稳定的版本/永久链接
  - 标注访问日期 (对于可能变化的内容)

示例:
  ✅ [Conventional Commits](https://www.conventionalcommits.org/v1.0.0/)
  ✅ [Flutter Docs](https://docs.flutter.dev/) (2025-12)
  ❌ [某文档](http://example.com/temp-link)
```

### 4.3 代码引用

```yaml
规则:
  - 引用的代码必须存在
  - 行号引用要准确
  - 版本变更后及时更新

格式:
  - 文件:行号 → "src/auth.py:42"
  - 函数引用 → "AuthService.validateToken()"
```

### 4.4 Issue / PR 引用写法

> 2026-09-13 起生效 (owner 裁定, 来源 `10CG/aria-plugin#196`)。

```yaml
规则 1 — 跨仓一律全限定:
  - 引用 issue / PR 一律写 <org>/<repo>#<n>, 例: 10CG/Aria#195
  - 原因: 同一个号在不同仓里常各有一条且互不相干
    (实例: 10CG/Aria#195 与 10CG/aria-plugin#195 是两件事);
    只写仓名、或只写 "#" 加数字, 读者无法确定指哪条

规则 2 — "#" 只留给 issue / PR:
  - 文内自己的编号 (待复议条目、表格行、清单项、步骤) 不用 "#", 直接写数字
  ❌ "待 owner 复议 #N-#M"    ✅ "待 owner 复议条目 5–7"
  ❌ 表格首列 "| #N |"        ✅ "| 18 |"
  ❌ "触点表 #N"              ✅ "触点表第 18 项"
  - 例外: 本项目规则编号 "Rule #N" / "规则 #N" 保持原写法
  - 原因: 机械检查分不清「文内编号」和「漏写仓名的 issue 引用」;
    让 "#" 只有一种含义, 检查才能保持从严而不误报

执行口径:
  - 新写或本次改动到的文字按上面两条写; 存量文档不做批量回改, 改到哪段顺手改哪段
  - 自检工具: aria-plugin 的 skills/state-scanner/scripts/check_bare_issue_refs.py <文件>
    (rc 0 = 无违规; 豁免仅三类: 全限定引用 / Rule #N / 调用仓 .aria/bare-issue-ref-allowlist.txt 所列字面)
  - 它是手动自检工具, 不是已启用闸门 (owner 2026-09-13 裁定暂不注册进 .aria/state-checks.yaml);
    在它成为闸门之前, Spec 不得把「整份文件 rc 0」写成验收门槛 —— 存量文字会让它恒红
```

### 4.5 文内编号用普通数字

> 2026-09-13 起生效 (owner 裁定)。

```yaml
规则:
  - 条目、步骤、选项、表格行、代码注释里的编号, 只用以下写法:
      阿拉伯数字 1 2 3 / 大写拉丁字母 A B C / ASCII 括号 (1) (2) / "1." "2."
  - 不用带圈、带框、带括号的单字符编号
    (Unicode U+2460–U+24FF、U+2776–U+2793、U+3251–U+325F、U+32B1–U+32BF 这几段)
  - 不用希腊字母做编号或标签
  - 例外: 专有名词本身含希腊字母的术语保留 —— 那是术语, 不是编号
  - 原因: 这类单字符编号在部分终端里字号过小, 看不清是几; 希腊字母中文输入法难打, 扫读要心算
  - 与 4.4 规则 2 一起看: 文内编号既不用 "#", 也不用上面这些字符, 一律普通数字

执行口径:
  - 新写或本次改动到的文字按本条写; 存量 (历史审计报告、归档 spec、CHANGELOG 旧条目、测试夹具等)
    不做批量回改, 改到哪段顺手改哪段
  - 暂无机械闸门。自查命令 (只查上面几段编号字符; 希腊字母因有合法术语, 不纳入):
      python3 -c 'import re,sys;[print(f"{f}:{i}: {l.rstrip()}") for f in sys.argv[1:] for i,l in enumerate(open(f,encoding="utf-8"),1) if re.search("[\u2460-\u24ff\u2776-\u2793\u3251-\u325f\u32b1-\u32bf]",l)]' <文件...>
    有输出即命中 (该命令 2026-09-13 实跑验证: 对含此类字符的文件报出命中, 对已清理文件无输出)
```

## 5. 示例数据规范

### 5.1 标识规则

```yaml
必须标识:
  - 所有示例数据
  - 模拟数据
  - 测试数据

标识方式:
  - 注释: "// 示例数据"
  - 前缀: "example_", "mock_", "test_"
  - 文档说明: "> 以下为示例数据"
```

### 5.2 示例数据要求

```yaml
要求:
  - 格式正确 (符合实际数据格式)
  - 逻辑合理 (数值、关系合理)
  - 不包含敏感信息

示例:
  ✅ email: "user@example.com"  // 示例
  ✅ phone: "138****1234"       // 脱敏示例
  ❌ password: "123456"         // 真实弱密码
```

## 6. AI 生成内容规范

### 6.1 标识要求

```yaml
需要标识的场景:
  - AI 辅助生成的文档
  - AI 建议的代码
  - AI 翻译的内容

不需要标识:
  - AI 格式化/重排
  - AI 拼写检查
  - 常规代码补全
```

### 6.2 标识方式

```yaml
文档:
  > 本文档由 AI 辅助生成，已经人工审核

代码注释:
  # AI-assisted: 此函数逻辑由 AI 建议

提交消息:
  # 禁止添加 AI 签名 (见 git-commit.md)
```

### 6.3 审核要求

```yaml
AI 生成内容必须:
  - 人工验证准确性
  - 确认符合项目规范
  - 测试功能正确性 (代码)
```

## 7. 版本和变更追踪

### 7.1 版本号规范

```yaml
格式: MAJOR.MINOR.PATCH

变更类型:
  - MAJOR: 重大架构/内容变更
  - MINOR: 新增章节/功能
  - PATCH: 修正/优化
```

### 7.2 Changelog 规范

```yaml
必须记录:
  - 版本号
  - 变更日期
  - 变更内容摘要

示例:
  changelog:
    - version: 2.0.0
      date: '2025-12-14'
      changes: 重构文档结构，添加AI内容规范
```

## 8. 违规示例

### 8.1 严重违规

```yaml
案例 1 - 虚假完成状态:
  ❌ "功能已完成，测试通过" (实际未测试)
  ✅ "功能开发完成，待测试"

案例 2 - 虚构数据:
  ❌ "覆盖率达到 95%" (实际 45%)
  ✅ "当前覆盖率 45%，目标 80%"

案例 3 - 错误日期:
  ❌ created_at: '2025-01-01' (实际 12月创建)
  ✅ created_at: '2025-12-14'
```

### 8.2 轻微违规

```yaml
案例 1 - 示例未标识:
  ⚠️ const user = { name: "John" }
  ✅ const user = { name: "John" }  // 示例数据

案例 2 - 链接未验证:
  ⚠️ [详情](./old-doc.md)  // 文件已移动
  ✅ [详情](./new-location/doc.md)
```

### 9.1 文档创建时

- [ ] 日期使用实际日期
- [ ] 人员信息使用角色描述
- [ ] 功能状态准确
- [ ] 示例数据已标识
- [ ] 链接已验证

### 9.2 文档更新时

- [ ] updated_at 已更新
- [ ] Changelog 已记录
- [ ] 旧链接已修正
- [ ] 状态信息同步

### 9.3 代码提交时

- [ ] 注释内容准确
- [ ] 测试数据已标识
- [ ] 无敏感信息
- [ ] 版本号正确
